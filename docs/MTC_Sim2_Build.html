01

What was built, in one paragraph

A consumer enrols and we mint them a Solana wallet whose key we hold; one $ACM lands in it and that token is their membership credential, nothing more. A brand funds an offer denominated in Walmart weeks. We push that consumer a Meme Token Credit — which is not a coin but an Apple Wallet pass carrying an HMAC-signed QR code. They walk into an arcade, the reader scans it, and that scan is the settlement event: the credit is extinguished exactly once, the product is handed over, and a row lands in an append-only hash-chained ledger. At the close of each Walmart week a Merkle root of that ledger is published to a public chain, so a brand can verify its own redemptions against a commitment nobody — including us — can revise.

The blockchain does exactly one job in this system: prove the holder has at least one $ACM. That is a read. Everything else is our ledger.
02

The Walmart-week spine

Every offer window, expiry and ledger period is denominated in Walmart weeks. This is not cosmetic. Walmart's trade team plans, funds and reports promotional dollars in these weeks, so a redemption ledger kept in the same weeks reconciles to a brand's own trade report with no translation step — no partial weeks, no allocation assumptions, no argument about which week a Tuesday redemption belongs to.

Why America/New_York and not EST

Strict "EST" is UTC−5 year-round. From March to November an offer set to expire Friday midnight would actually die at 1:00 a.m. local — an hour the customer believes they still have. The named zone observes the DST shift, so Friday midnight is midnight on the wall clock every week of the year.

The 53-week year, handled without a special case

# A fiscal year runs until the next one starts. The week count falls out
# of the two anchors, so a 53-week year needs no special case anywhere else.
def fy_start(fiscal_year):
    anchor = date(fiscal_year - 1, 2, 1)          # FY2027 -> Feb 2026
    return anchor - timedelta(days=(anchor.weekday() - SATURDAY) % 7)

def fy_weeks(fiscal_year):
    return (fy_start(fiscal_year + 1) - fy_start(fiscal_year)).days // 7

03

HMAC on every channel

QR payloads, reader-to-server reports, brand submissions, webhooks, internal calls. One standard, no per-case decision.

A random token requires the verifier to ask a server whether it is real. An HMAC-signed token verifies OFFLINE, with no network at all.

That is load-bearing: Starlink is the arcade site minimum, but a scanner that stops working during an outage stops the entire promotion. Signed codes mean the worst case is delayed reconciliation, not a dead lane.

05

Wallet minting — the noob path

Solana does not mine keys. Bitcoin's proof-of-work orders transactions; it has nothing to do with creating a key. A Solana private key is literally 32 random bytes, and the public address is derived from it mathematically, offline, in microseconds. There is nothing to search for and no network call involved in creating one.

1. 32 bytes from the OS CSPRNG        (SecRandomCopyBytes on macOS)
2. derive the ed25519 public key      -> that IS the address, offline
3. confirm the address has never been used
4. push 1 $ACM                        -> the eligibility credential
Step 3 is not about collisions. Colliding with an existing wallet is 1 in 2²⁵⁶. It is about catching a broken RNG on our side — and a bug in our own randomness is nowhere near 1 in 2²⁵⁶. One cheap call turns a silent catastrophic failure into a loud one.

Two things flagged, not solved

Custody. Holding the key on the user's behalf is custody, with the regulatory posture that implies. The architecture is positioned for it — MTC carries no cash value and $ACM is never spendable inside the system — but "we can revoke it" and "the user owns it" are different claims and only one can be true. This is a specific question for Wood Herron, not a footnote.

Key storage at scale. The simulation writes keys to a local file. That is fine for a simulation and wrong for production: N independent keys means N secrets to protect and one breach exposes everyone. Production wants hierarchical deterministic derivation — one master seed in an HSM, each user's key derived by index — so there is one secret to guard and no database of private keys exists to steal.

The ledger is the product

KRW-C-2026-002: "The measurement is not a product built alongside the system. It is what the system leaves behind." Every state change goes through the ledger. There is no other write path, and the ledger has no update and no delete.

# Hash over every field INCLUDING the previous hash. Order is part of the
# contract — change it and every historical hash becomes unverifiable.
def _hash_row(seq, utc, fy, week, event, subject, detail, prev_hash):
    blob = json.dumps([seq, utc, fy, week, event, subject, detail, prev_hash],
                      separators=(",",":"), sort_keys=True)
    return hashlib.sha256(blob.encode()).hexdigest()

Altering any historical row changes every hash after it, and the break is detectable by anyone holding a later hash. Verified on a tampered file:

clean chain     : (True, None, 5)
after tampering : (False, 3, 5)      <- detected at that sequence number

Why git alone is not enough

Git is hash-chained and therefore genuinely tamper-evident. But history can be force-pushed and rewritten by anyone with write access, and nothing inside the repository would prove it happened. So a Merkle root is published per Walmart week:

The repository holds the data. The chain holds the proof that the data has not moved. A brand verifies its own redemptions against an anchor nobody controls — including us.

Scoping the anchor to a week is deliberate: the root published at week close commits exactly that week's settlement facts, which is the period the brand's trade report is denominated in.

The offline tradeoff, stated rather than discovered

Offline validation proves a code is authentic and unexpired with no network. It cannot check whether the code was already spent — that needs the ledger. So an offline scan is queued and reconciled when the link returns, accepting a small double-redemption window rather than letting an outage stop the lane. That is a business decision and it should be made deliberately, not found later.

The simulation caught a bug on its first run — an invented rule

An earlier draft refused any offer running past fiscal year end. That silently made a 52-week offer impossible unless it began in week 1, and PG-OLAY failed immediately. The stated rule is duration: 1 to 52 weeks from wherever it starts. The window now rolls into the next fiscal year and reports the closing week in the year it actually lands in — which is why PG-OLAY reads WK27 + 52 → FY2028 WK26.
